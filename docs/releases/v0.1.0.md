# Skills Manager v0.1.0 — Public Preview

Skills Manager helps users install and update Agent Skills without losing the changes they want to keep. A Patch is one user-approved result that remains protected across Updates.

## Patch-only experience

- Need-aware discovery and recommendation lead to approval of the exact Skill selection before installation.
- One human-readable Patch document belongs to one exact Installation and contains only uniquely titled Active Patches with required outcomes and optional rationale or constraints.
- Project and global documents are independent and bind to upstream source, Skill identifier, and Installation scope rather than a display name or physical path.
- Update resolves identity and readable durable state before upstream mutation, then preserves every Active Patch together. Implementation details may adapt; semantic changes require user approval.
- Already-satisfied Patches remain active. Conflicting, ambiguous, or unsafe Patches remain intact while Skills Manager explains the concrete Conflict and waits for the user.
- One-off unmanaged edits remain possible after the user is told that Update may overwrite them. Local Skill changes remain at their user-owned source.
- Removing an Installation's final target removes its Patch document after confirmation. Batch results remain independent, and Skills Manager self-Update is rejected while it has Active Patches.

This release is a breaking reset of the earlier Public Preview customization format. That format is unsupported: there is no compatibility reader, automatic conversion, or migration workflow.

## Distribution and compatibility

- Node.js 22 and 24 (`>=22`)
- `npx skills >=1.5.19 <2.0.0`
- GitHub installation through `npx skills`; no npm package distribution
- Native source, no runtime dependencies, runtime helper, or build step

Before publication, the exact tag target must pass both compatibility endpoint smokes, deterministic Node 22/24 checks, distribution policy, DCO, and the full-history secret scan. Publishing the tag and changing repository visibility remain manual maintainer actions.

See the [security policy](../../SECURITY.md) for private vulnerability reporting.
